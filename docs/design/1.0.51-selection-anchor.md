# 1.0.51 设计：以选中框锚点验证滚轮逐行推进

> 实施补充（2026-11-25–26）：本机当前库存为 990 件。现场发现旧结构签名按列表高度四等分（约 171px），与真实 175px 行距不一致；原图确认的一行位移会被判为强 NoMove。因此旧签名保留供 off/回退，锚点事务另用真实行距、相同卡片内部区域作结构复核，仍拒绝可靠的结构冲突。检测阈值由初值 70 调为 85，避免合成的四分之一行过渡框被读为唯一锚点；真实稳定帧仍为 100 分。释放阶段只需两个稳定帧，不重复累计第三帧。
>
> 另外：零移动必须与独立底部证据共同成立，本实现使用两帧滑块到达轨道末端（只判到底，不用其微小位移数行）；仅两个滚轮无效不能宣告到底。`wheel_anchor_accepts_explained` 同时进入最终 correctness 和退出码。调试库存偏移的预期 partial 作为专门的失败路径验收，不豁免普通扫描的完整性门禁。性能采用同日同起点基线；完整性比较物品内容与重复次数，不只比较逻辑行计数。

## 1. 背景

### 1.1 游戏行为变化与 1.0.49 默认路径失效

1.0.49 两个内置 profile 默认 `NativeEdgeClick`：点击视觉第 4 行，靠游戏原生下推。游戏更新后点击第 4 行不再滚动，1.0.49 的默认路径会这样走（按代码推断，P0 用 1.0.49 默认 profile 实跑一次确认）：

1. `AdvanceNativeEdgeClickAsync` 点击后列表不动 → `Unchanged` → `HashFallback`；
2. 重新扫描“新的”视觉第 3 行（其实还是同一行），详情指纹与上次相同 → 判为 `Bottom`；
3. 扫视觉第 4 行后，因访问数与库存数不一致，以 `inventory_count_mismatch_at_observed_bottom` 输出 partial。

也就是说，当前游戏下 1.0.49 默认配置在**第一屏之后就停止**。网页（Helper）扫描使用 profile 默认值，同样受影响；只有显式 `--row-advance-mode wheel` 才能完整扫描。因此 1.0.51 的第一件事是把默认推进方式改回滚轮。

### 1.2 1.0.49 的滚轮推进流程

入口：`ProduceCapturesOverlapSignaturePageAsync`（`Scanning/ScanController.cs` 约 932 行）在非 `NativeEdgeClick` 时调用 `ScrollSafeBandOneRowWithRetryAsync`（约 2517 行）→ `ScrollSafeBandOneRowAsync` → `ScrollVerifiedRowShiftAsync`（约 2621–2936 行）。一次事务：

1. **基线**：光标移到列表右侧空白 `ListNeutralPoint`，抓取整个 `listGridRect`（`CaptureViewportSignatures`，四行 24×8 结构签名 + 全网格签名），并读取滚动条滑块 `CaptureScrollbarThumbProbe`，算出“每行对应滑块多少像素”`ScrollbarPixelsPerLogicalRow`。
2. **发滚轮**（`RowScrollCoordinator.RunAsync` 的 `issueWheelAsync`）：光标移到 `listWheelArea`(690,520)，等 40ms，发 1 个 `-120` 刻度，再等 `scrollTickDelayMs`(80ms)；光标**留在列表上**（1.0.46 起：过早移开会让新版平滑滚动停在吸附门槛前并回弹）。
3. **取证**（快速探测最多 3 帧，随后最多 500ms 无输入稳定期）：每帧计算 0/1/2 行三种对齐的结构分（`VerifyOneRowDown` + `RowAdvanceEvaluator.Evaluate`），再用滚动条位置调和（`RowAdvanceEvaluator.ReconcileScrollbarPosition`）；另外**若滚动条估算超过 1.5 行，直接改判为强两行**（`scrollbar_overshot_above_single_row_limit`）。
4. 连续 2 帧稳定的 1/2 行结论被接受（`EarlyOneRow` 模式下强结构一行可单帧接受）；确认 0 行位移且满 3 帧时允许发第 2 个刻度（事务上限 2 个刻度）。
5. **释放复核**：光标移回空白处，最多 6 帧，要求连续 2 帧相同的 1/2 行结论，才提交逻辑游标。
6. 下行只接受 `rowsAdvanced == 1`；两行 → `ROW_SCROLL_OVERSHOT_BLOCKED` 停止；歧义 → `ROW_SCROLL_AMBIGUOUS_STOP` 停止；两刻度都没动 → `scroll_no_movement_after_max_ticks` 停止。

### 1.3 1.0.49 滚轮判定的弱点

| 编号 | 弱点 | 证据 / 后果 |
| --- | --- | --- |
| W1 | 滚动条证据太弱，却有“一票否决”权：1080p 下一行只对应约 6.4px 滑块位移（806 件时），悬停、动画、取整都在同一量级；超过 1.5 行直接判两行停止，判 0 行但网格动了则判歧义停止。 | 2026-11-05（`test/1.0.50:docs/TESTING.md`）同日 1.0.49 `WheelVerified` 有 2 轮分别在第 27、36 件停止，原因 `scrollbar_overshot_above_single_row_limit` 和 `scrollbar_grid_movement_conflict`。每行 9 件，正好是第 1、2 次滚动。 |
| W2 | 行结构签名在相邻行外观相同时分不出 0/1/2 行（`insufficient_margin`）。 | 相同 +0 盘成片时只能靠滚动条，又回到 W1。 |
| W3 | 两个刻度都没动时直接失败，没有“到底”路径。 | 库存数量 OCR 偏大时整轮以导航失败结束，而不是按观察到底输出 partial。 |
| W4 | 取证时光标停在列表上，悬停与平滑滚动动画会干扰结构签名。 | 1.0.46/1.0.47 为此加了无输入稳定期与释放复核，代价是等待时间。 |

### 1.4 为什么不沿用 1.0.50 的相位探针

1.0.50 的 `PhaseVerified` 正是为解决 W1 而做：不看滚动条，看列表边缘周期条带是否“离开再回来”。它在 200 件规模上 6/6 通过，速度与 1.0.49 滚轮持平。但 ZZZ 一个刻度就是一整行（1.0.50 实测 `avg_ticks_per_row=1.00`），相位信号以行距为周期，滚 1 行和滚 2 行停下时都“回到原相位”。用“一次手势两次循环”识别越滚需要在动画中途连续采到 2 帧对齐，而实测约 30ms/帧，基本不会触发，真实两行越滚也从未复现。所以相位只能确认“已对齐、已停稳”，**不能数行**；1.0.50 的行数仍要靠旧的行结构签名兜底。1.0.51 改用能直接给出行号的选中框锚点。

### 1.5 外部参考

- **tim883/zzz-ddtool**（绝区零驱动盘强化工具，2026-11 仍在维护）的**生产路径就是“滚轮 + 选中框锚点”**：
  - 先点一个已知格子作为锚点，确认它唯一被选中；
  - 发 1 个滚轮事件，每个事件 = 1 行；
  - 轮询直到锚点所在屏幕行连续两次一致；
  - 前后行差就是实际前进行数。

  对应代码：`runner.py::_advance`、`navigation.py::scroll_rows/settle_and_read_anchor/anchor_screen_rows`、`equipped.py::tile_is_selected`。其文档明确禁止用滑块推算行数，到底需要“实际位移小于请求”与“末尾空位连续”两条证据。这说明**选中框在滚轮滚动后仍保留在原格子上**，本设计的核心假设已有一个生产实现在同一界面上验证过。
- **本仓库 `codex/scanner-native-gamepad`**（`c6c23d7`，未发布实验）的 `Scanning/GamepadFocusDetector.cs`：用连通域找焦点框，注释记录了“脉冲在 lime/yellow 间交替、S 级色条 G/R≈0.71 不在色带内”。手柄注入需要 MSIX 签名，不进入 1.0.51；检测思路作参照。

## 3. 总体设计

### 3.1 一句话原理

扫描时每点开一张盘，它就带上选中框，全屏只有一个。每次滚轮前，在整个网格里找到这个选中框的位置 `(r0, c)`；滚轮后，在第 `c` 列找它的新行号 `r1`。前进行数 `k = r0 - r1`：

- `k = 1`：恰好一行，提交；
- `k = 0`：没动，按“刻度被吞/到底”处理；
- `k = 2`：两行，停止（与现有严格单行规则一致）；
- 找不到或不唯一：证据不足，退回 1.0.49 的判定（verify）或停止（strict）。

选中框是唯一的，不受“相同的盘长得一样”影响；它给出的是格子的绝对行号，不需要在动画中途采样，也不依赖滚动条。

### 3.2 证据层级（verify 模式）

| 本次事务是否有可用锚点 | 决定行数的证据 | 行结构签名 | 滚动条 |
| --- | --- | --- | --- |
| 有（基线唯一且 `r0 ≥ 2`） | **锚点** | 只用于发现矛盾（强证据与锚点不一致 → 停止） | **只记录日志，不参与判定**（W1 的两类误停因此消失） |
| 无 | 与 1.0.49 完全相同（结构 + 滚动条） | 同 1.0.49 | 同 1.0.49 |

列表置顶复位按用户后续要求增加锚点确认：顶部颜色与滑块几何只完成粗判，随后选择第二行锚点，至少两次向上输入后仍在原行、内容及帧稳定且顶部标记成立，才建立绝对位置并开始采集。深列表最多两轮有界恢复，第二轮放慢输入以减少吞刻度。

### 3.3 运行模式

新增 `SelectionAnchorMode { Off, Shadow, Verify, Strict }`，作用于 `WheelVerified` 的下行滚轮事务：

| 模式 | 计算锚点 | 影响决策 | 锚点不可用时 | 用途 |
| --- | --- | --- | --- | --- |
| `off` | 否 | 否 | — | 等同 1.0.49 `WheelVerified`；紧急回退 |
| `shadow` | 是 | 否 | — | P2 收集一致性数据；记录“锚点能否挽救 1.0.49 的误停” |
| `verify` | 是 | 有锚点时按 §3.2 | 退回 1.0.49 判定，记录 `WHEEL_ANCHOR_FALLBACK` | 1.0.51 目标默认值 |
| `strict` | 是 | 同 verify | 直接停止（partial） | 验收与排查 |

模式来源优先级（从高到低）：

1. 环境变量 `ZZZ_SCANNER_SELECTION_ANCHOR=off|shadow|verify|strict`：现场紧急开关，不改 profile、不发新版就能关闭；
2. CLI `--selection-anchor <mode>`；
3. profile 字段 `selectionAnchorMode`；
4. 默认 `off`（profile 缺字段时保持 1.0.49 行为）。

解析写成纯函数 `SelectionAnchorModeResolver.Resolve(options, profile, environment)` 并单测（吸取 1.0.50 P0-1 的教训，见 §15）。`Start scan.` 日志追加 `SelectionAnchorMode=<mode>, SelectionAnchorSource=env|cli|profile|default`。`NativeEdgeClick` 下该模式被忽略，并记录 `SELECTION_ANCHOR_IGNORED reason=row_advance_mode_not_wheel`。

### 3.4 默认推进方式切回滚轮

- `Data/scan_profiles.json` 两个 profile：`rowAdvanceMode: "WheelVerified"`，`selectionAnchorMode` 在 P2 为 `shadow`、P3 门禁通过后为 `verify`。
- P2 的“滚轮 + shadow”已经能修复 §1.1 的默认失效（只是还带着 W1 的偶发误停）。如果 P3 延期，可以先单独发一个只切默认推进方式的修复版本（见 §16）。
- `NativeEdgeClick` 的处理见 §6。

## 4. 选中框检测器

新文件 `Scanning/SelectionAnchor.cs`，纯函数、不依赖窗口与输入，便于离线评估与单元测试。

### 4.1 几何（以 1920×1080 设计坐标表示，运行时按客户区比例缩放）

```
tileCenter(col, row) = driveDiscOffset + driveDiscStep × (col, row) + selectionTileCenterOffset
selectionTileCenterOffset 初值 = (-49, -53)        // F2，P0 校准
```

缩放与现有 profile 点位一致（`window.ToScreenPoint`）；带宽、步长等长度乘以 `客户区高度 / 1080` 后取整，最小 1px。

| 参数 | 初值（1080p） | 依据 |
| --- | --- | --- |
| 左竖带横向范围 | 中心 -70 … -54 | F4 左边 -66…-59；不超过 -70，避开左邻格右边框（约 -75…-68） |
| 右竖带横向范围 | 中心 +54 … +70 | F4 右边 +60…+67；右邻格左边框约 +69…+77，靠双边与对称约束排除 |
| 纵向采样范围 | 中心 -20 … +44 | F5 共同覆盖段约 -24…+64；上避徽标与头像，下离底部色条（约 +51）留距 |
| 纵向采样步长 | 4px | 每边 17 点 |
| 横向搜索步长 | 1px | 每条竖带 17 列候选 |

### 4.2 像素判据

转 HSV，同时满足以下三条即为“框色像素”：

| 参数 | 初值 | 依据 |
| --- | --- | --- |
| 色相 | 45° ≤ H ≤ 100° | 黄 54°、黄绿 72°、HDR 黄 60°；排除常规 S 色条 42.6°。HDR 色条同为 60°（F8），但它只在底部横向出现，不在竖带采样段内，由几何排除 |
| 饱和度 | S ≥ 0.55 | 未选中描边 S≈0（F6） |
| 亮度 | V ≥ 0.45 | 排除暗背景噪声 |

阈值放入 profile（§7.3），P0/P1 用夹具和现有 14 种色彩变换矩阵校准后定稿。

### 4.3 单格评分

对一条竖带：在带内每个候选 x 上统计 17 个纵向采样点中框色像素的占比，取占比最高的一列作为该边位置 `edgeX` 与覆盖率 `coverage`（同 zzz-ddtool，对线宽、缩放、1px 偏移稳健）。

```
score = round(100 × min(leftCoverage, rightCoverage))
asymmetry = |(center.X - leftX) - (rightX - center.X)|
若 asymmetry > maximumAsymmetry（初值 8px@1080p），score = 0
```

只有左右两边同时成立才得高分；邻格的单侧框线、底部横向色条、单侧图标都无法得分。

### 4.4 两种查询

| 查询 | 用途 | 规则（初值） |
| --- | --- | --- |
| `FindUnique(frame, geometry)`：全网格 9×4 | 滚动前基线，找出选中格 `(r0,c)` | 恰有一格 ≥ `minimumScore`(70) 且其余格都 ≤ `maximumOtherScore`(30) → `Unique(r0,c)`；两格以上 ≥70 → `Multiple`；最高分 30–70 或次高分 30–70 → `Weak`；全部 <30 → `None` |
| `ObserveColumn(frame, geometry, c)`：单列 4 行 | 滚动后跟踪 | 同样规则，只在第 `c` 列内判定 |

返回结构：

```csharp
internal readonly record struct SelectionAnchorCellScore(
    int Row, int Column, int Score, double LeftCoverage, double RightCoverage,
    int LeftX, int RightX, int Asymmetry);

internal sealed record SelectionAnchorObservation(
    SelectionAnchorVerdict Verdict,     // Unique / Multiple / Weak / None
    int? Row, int? Column,              // 仅 Unique 时有值
    int BestScore, int SecondScore,     // 无数据为 -1，不编造
    IReadOnlyList<SelectionAnchorCellScore> Cells,   // 日志只输出前 4 名
    double DetectMilliseconds)
{
    public string Format();
}
```

### 4.5 性能：复用同一帧

1.0.49 每次滚轮取证都调用 `CaptureViewportSignatures`，抓一整张 `listGridRect`。检测器**复用这一帧**，不增加截图次数：

- 新增 `CaptureViewportObservation(window, listGridRect, rowSignatureRects, SelectionAnchorRequest?)`：抓 `listGridRect` 左右各外扩 8px（缩放后）的矩形。外扩的原因：第 9 列右竖带在 1080p 约到 x=1316，超出 `listGridRect.Right=1312`。行签名与全网格签名仍只在原 `listGridRect` 子区域上计算，保证与 1.0.49 结果一致（T15 断言）。
- 计算量：单列查询 4×2×17×17 ≈ 2300 次像素读取，全网格查询约 2 万次。只有基线做全网格，DXGI raw 下 <1ms；GDI 位图路径用 `LockBits` 读取，不用 `Bitmap.GetPixel`。
- 锚点事务中，滚动条只在基线与最终提交时各读一次，用于日志，取证帧不再逐帧读取，可以略微省时。

### 4.6 已知干扰与处理

| 干扰 | 处理 |
| --- | --- |
| HDR 下 S 色条与选中框同色（F8） | 只采样左右竖带中段 |
| 黄 ↔ 黄绿脉冲（F3） | 色带同时覆盖；覆盖率 0.70；连续 2 帧一致才算数 |
| 装备头像、编号徽标压住上角（F5） | 纵向采样从 -20 开始 |
| 弃置、锁定图标（格子内部右下） | 不在竖带上 |
| 邻格被选中 | 双边 + 对称约束 |
| 平滑滚动中途 | 框不在任何行的标准位置，各行都只得低分 → `Weak/None`，不会形成连续两帧 `Unique` |
| 悬停高亮（Q1） | 取证阶段锚点只作为暂定证据；**提交只看光标移回空白处后的释放阶段读数**（§5.6） |
| 游戏更新改了选中框样式 | 基线找不到锚点 → verify 退回 1.0.49；`wheel_anchor_unavailable` 计数立即暴露；用 `--selection-anchor-eval` 截一张图即可确认 |

## 5. 与 WheelVerified 的集成

### 5.1 时序总览

```
[当前视口候选行已扫完，列表稳定]
 (1) 光标 → 列表右侧空白（1.0.49 已有）
 (2) 基线帧：行签名 + 全网格签名 + 全网格锚点查询 + 滚动条（日志用）    WHEEL_ANCHOR_BASELINE
     └─ 无可用锚点 → 主动锚点：点击第 3 行一个已扫格子，重读基线          WHEEL_ANCHOR_ARM
        └─ 仍无 → 本次事务按 1.0.49 原逻辑（verify）/ 停止（strict）       WHEEL_ANCHOR_FALLBACK
 (3) 发刻度（不变：光标到 listWheelArea，等 40ms，-120，等 80ms，光标留在列表上）
 (4) 快速探测 + 无输入稳定期（不变的协调器）：证据 = ReconcileAnchor(结构, 第 c 列锚点)
 (5) 光标 → 空白处；释放复核：连续 2 帧相同结论，且锚点唯一                 WHEEL_ANCHOR_RELEASE
 (6) 决策（纯函数）→ 提交一行 / 第二个刻度 / 观察到底 / 停止               WHEEL_ANCHOR_DECISION
```

### 5.2 第 2 步：基线与锚点来源

**被动锚点**（零额外输入）：扫描中最后一次点开的盘就是选中格。中部状态扫的是视觉第 2、3 行，所以通常 `r0 = 3`；首屏扫第 1–3 行，也是 `r0 = 3`。不靠记账，直接对基线帧做全网格 `FindUnique`：面板重试、邻格往返（`PANEL_NEIGHBOR_ROUNDTRIP`）、首对见证都会额外点击别的格子，用检测结果比记账更可靠。

实施时复用 `CELL_CLICK`/`CELL_TIMING`，并通过 `ITEM_POSITION_VERIFIED` 记录不可变的已验证位置；没有另设 `lastAcceptedClickCell`。滚轮基线始终用当前帧全网格检测结果，避免把首对见证与邻格往返之前的点击位置当作当前选中格。

可用性规则：

| 基线结果 | 能检测的前进行数 | 处理 |
| --- | --- | --- |
| `Unique(r0 ≥ 3, c)` | 0/1/2 行全部可直接读出 | 使用 |
| `Unique(r0 = 2, c)` | 0/1 行可读；2 行时锚点滚出视口变成 `None` | 使用；滚后 `None` 且结构强两行 → 判两行（§5.5） |
| `Unique(r0 = 1)`、`Unique(r0 = 4)`（理论上中部不会出现）、`Multiple`、`Weak`、`None` | — | 走主动锚点 |

**主动锚点**：点击视觉第 3 行、第 `columns` 列（最后一列）的格子。这一行已经扫过，点击只会改变详情面板，不影响已入队数据。点击后等 `max(80, clickDelayMs)` 并等列表稳定（`WaitForListStableAsync`），再重读基线。前提是 Q6 证实点击第 3 行不引起滚动；若 Q6 发现第 3 行也会滚动，则改点第 2 行（此时 `r0 = 2`）。

- 记录 `WHEEL_ANCHOR_ARM reason=baseline_none|multiple|weak|row_too_high, cell=(3,c)`。
- 主动锚点后仍不可用：verify 按 1.0.49 原逻辑完成本次事务并记录 `WHEEL_ANCHOR_FALLBACK reason=baseline_unavailable`；strict 停止。
- 预计触发频率：只有视觉第 3 行没有任何 S 级（全被筛选跳过、未点击）且其他点击也不在第 3 行时才需要。806 件账号中 A 级共 40 件（1.0.49 实测），整行全为 A 级的情况很少。`--anchor-force-active` 调试参数用于专门测试这条路径。

### 5.3 第 3–4 步：发刻度与取证

发刻度的动作完全不变（必须保留“光标留在列表上”以免回弹）。

取证回调（`captureObservationAsync`）在锚点事务中改为：

1. `CaptureViewportObservation` 抓一帧，得到行签名、全网格签名、第 `c` 列锚点观察；
2. 结构证据：沿用 `VerifyOneRowDown` + `RowAdvanceEvaluator.Evaluate`；
3. 合成：`RowAdvanceEvaluator.ReconcileAnchor(structural, anchorObservation, r0)`（§5.4），**替代** `ReconcileScrollbarPosition` 和“滚动条超过 1.5 行改判两行”的覆盖；
4. 返回 `RowScrollObservation(evidence, frameDistance, ScrollbarPixelDelta: null, AnchorRowsAdvanced: k?)`。

`RowScrollCoordinator` 不改流程，只扩展一处：`RowScrollObservation.ConfirmedZeroMovement` 原来要求 `ScrollbarPixelDelta == 0`，改为“`ScrollbarPixelDelta == 0` **或** `AnchorRowsAdvanced == 0`”。这样刻度被吞时（锚点仍在 `r0`、网格稳定 3 帧）仍能触发 `retry_after_full_no_move_window` 发出第 2 个刻度。

取证阶段光标在列表上，可能有悬停干扰（Q1），所以这个阶段的锚点结论只作为**暂定证据**，决定协调器何时进入释放复核；**最终行数只取释放阶段的读数**。

### 5.4 `ReconcileAnchor` 规则

输入：结构证据 `S`（决策、强弱、`MovedDistance`），锚点观察 `A`，基线行 `r0`。输出 `RowAdvanceEvidence`（沿用现有记录类型，`Reason` 以 `anchor_` 开头）：

| # | 锚点 | 结构证据 | 输出决策 | Strong | Reason |
| --- | --- | --- | --- | --- | --- |
| A1 | `Unique(r1)`，k=r0-r1=1 | OneRow，或 Ambiguous，或弱 TwoRows/NoMove | OneRow | true | `anchor_1_row_confirmed`（结构不一致时追加 `_structure_weak`） |
| A2 | k=1 | **强** TwoRows 或 **强** NoMove | Ambiguous | false | `anchor_structure_conflict` |
| A3 | k=0 | `MovedDistance ≤ MovementTolerance(6)` | NoMove | true | `anchor_no_move_confirmed` |
| A4 | k=0 | `MovedDistance > 6`（网格动了而锚点没动） | Ambiguous | false | `anchor_grid_movement_conflict` |
| A5 | k=2 | 非强 OneRow / 非强 NoMove | TwoRows | true | `anchor_2_rows_confirmed` |
| A6 | k=2 | 强 OneRow 或强 NoMove | Ambiguous | false | `anchor_structure_conflict` |
| A7 | k<0 或 k≥3 | 任意 | Ambiguous | false | `anchor_impossible_shift` |
| A8 | `None`，且 r0=2 | 强 TwoRows | TwoRows | true | `anchor_left_viewport_two_rows` |
| A9 | `None` / `Multiple` / `Weak`（其余情况） | 任意 | **结构证据原样** | 原样 | 原 Reason + `_anchor_unavailable` |

说明：

- A9 在取证阶段属于正常现象（动画中途、悬停）。协调器会继续取样，所以不会因为一帧 `None` 就失败。
- 锚点事务里**没有**任何以 `scrollbar_` 开头的理由，`UsesScrollbarPosition` 为 false。A1 的强一行在 `EarlyOneRow` 模式下允许单帧提前进入释放复核；释放复核仍要求 2 帧。
- “强证据”沿用 `RowAdvanceEvaluator` 现有定义（`BestScore ≤ 48` 且 `Margin ≥ 18`）。

### 5.5 第 5–6 步：释放复核与最终决策

光标移回 `ListNeutralPoint` 后（1.0.49 已有），释放复核在锚点事务中改为：

- 每帧用同一合成函数 `ReconcileAnchor`；
- 通过条件：连续 `VerifiedScrollReleaseStableFrames`(2) 帧网格稳定、决策相同，**且**这两帧锚点都是 `Unique`、行号相同；
- 取样上限从 6 帧提高到 `anchorReleaseMaxSamples`(12，约 180ms@15ms 轮询)；P2 的 shadow 数据若显示 6 帧足够，就保持 6。

最终决策（verify / strict）：

| # | 释放阶段结论 | 动作 |
| --- | --- | --- |
| D1 | OneRow（A1） | 提交 +1：`ROW_SCROLL_DONE decision=OneRow, reason=anchor_1_row_confirmed`，随后 `OVERLAP_SCROLL_ACCEPTED rowsAdvanced=1`（与 1.0.49 字段一致） |
| D2 | TwoRows（A5/A8） | 沿用 1.0.49：`ROW_SCROLL_OVERSHOT_BLOCKED reason=strict_single_row_path, evidence=anchor` 后停止 |
| D3 | NoMove（A3），且协调器两个刻度都确认未动 | 观察到底路径（§5.7） |
| D4 | Ambiguous 冲突（A2/A4/A6/A7） | `WHEEL_ANCHOR_CONFLICT` 后停止（与 1.0.49 歧义停止一致，`ROW_SCROLL_AMBIGUOUS_STOP` 照常写出） |
| D5 | 释放阶段锚点始终不唯一（A9） | verify：按 1.0.49 原逻辑对**同一组**释放帧重新判定（结构 + 滚动条），记录 `WHEEL_ANCHOR_FALLBACK reason=release_anchor_unavailable`；strict：停止 |
| D6 | 协调器在取证阶段就以 AmbiguousStop 结束，但锚点暂定结论为 A1 | **仍进入释放复核**，由释放阶段锚点决定（这正是 W1/W2 误停被挽救的路径）；记录 `WHEEL_ANCHOR_RESCUE reason=<原歧义理由>` |

D6 需要改动 `ScrollVerifiedRowShiftAsync`：1.0.49 只有 `result.Accepted` 或“强证据稳定期超时”（`RowScrollReleasePolicy.TryCreateSettleTimeoutProvisional`）才进入释放复核；锚点事务新增第三个入口：“最后一个暂定锚点结论为 `Unique` 且 k=1”。这个入口只能导致提交 +1 或停止，不会因此多发滚轮。

**shadow 模式**：决策始终按 1.0.49。另外用同一批帧计算锚点结论，记录：

- `WHEEL_ANCHOR_SHADOW agreement=true|false|na`：锚点行数与 1.0.49 最终行数是否一致；
- `wouldRescue=true`：1.0.49 因歧义、冲突、滚动条覆盖而停止，但锚点在释放阶段给出了唯一一行。P2 用它量化 W1 的实际改善。

### 5.6 刻度被吞

锚点仍在 `r0` 且网格稳定（A3），协调器满 3 帧后发第 2 个刻度（1.0.49 机制，上限 2 个刻度不变）。第 2 个刻度后按正常流程判定；两个刻度都确认未动 → D3。

### 5.7 观察到底路径（D3）

滚轮推进只在 `visibleTopLogicalRow < maxVisibleTop` 时发生，也就是库存数量 OCR 认为还有更多行。两个刻度确认未动仍不能单独证明到底；还必须有连续两帧滑块位于轨道末端的独立证据。两者共同成立时，1.0.51 才进入“观察到底”，并共用 `ScanObservedBottomRowAsync` 读取末行；否则停止并保留部分结果。

1. 记录 `WHEEL_ANCHOR_BOTTOM_CONFIRMED ticks=2, anchorRow=r0, inventoryCount, visibleTopLogicalRow`；
2. 扫视觉第 4 行（`logicalRow = visibleTopLogicalRow + 3`，`treatBlankAsEnd: true`）。当前游戏点击第 4 行不会滚动（F11，Q6 复核），列表也已到底；
3. 访问数与库存数不一致时，`StopReason = inventory_count_mismatch_at_observed_bottom`，输出 partial。这段逻辑现在写在 `NativeEdgeClick` 分支里，抽成共享函数 `ScanObservedBottomRowAsync` 后两条路径共用。

off、shadow 模式以及锚点不可用的事务，仍按 1.0.49 失败处理。

### 5.8 边界情况

| 情况 | 处理 |
| --- | --- |
| 单屏列表（`totalRows ≤ 4`） | 不滚动，不调用锚点 |
| 已在 `maxVisibleTop` | 不滚动，不变 |
| 上行恢复 `ScrollSafeBandOneRowUpAsync` | 默认路径不使用（`allowScrollRecovery=false`），1.0.51 不改 |
| 列表置顶 `ResetListToTopAsync` | 粗判后以第二行锚点验证到顶，确认前不建立绝对位置 |
| 首对事务、邻格往返、面板重试 | 会额外点击，选中格可能不在最后扫描的格子；基线用全网格检测，不受影响 |
| 扫描取消、暂停 | 新增等待使用同一 `CancellationToken`，不新增线程 |
| 输入守卫（`WarehouseContextGuard`） | 主动锚点点击走 `GameWindow` 现有 API，自动受保护 |
| 滚动后新视觉第 3 行首格 | 选中框已随旧第 3 行移到第 2 行，新第 3 行首格点击会产生正常详情变化，**不需要** `NativeEdgeClick` 那样的选择态重置 |

### 5.9 性能预期

| 项目 | 变化 |
| --- | --- |
| 基线 | +1 次全网格检测（<1ms，DXGI），不新增截图 |
| 取证帧 | 不再逐帧读取滚动条（每帧少一次 5×620px 截图），加单列检测（<0.2ms） |
| 释放复核 | 要求锚点 2 帧一致；与原有 2 帧稳定要求重叠，预计不增加帧数 |
| 主动锚点 | 少见，每次约 100–200ms |
| 误停 | 消除 W1 两类误停，不再需要整轮重跑 |

目标：200 件 DXGI fast 与 1.0.50 同条件下的 1.0.49 滚轮基线（54.0–55.6s）相比不慢于 2%。

### 10.2 `--selection-anchor-eval`（P1）

- 输入单张 PNG 或目录；有 manifest 时逐项比对，没有时只输出分数。
- 输出：`file, verdict, row, column, best, second, top4=...`，最后一行 `mismatch_count`；有不一致时退出码 1。
- 用途：阈值校准；游戏更新后截一张图就能确认检测器是否仍然有效。

### 10.3 `--wheel-anchor-probe`（P2/P3）

- 结构与 1.0.49 `--edge-scroll-probe` 相同：持有扫描互斥锁、完成仓库预检、置顶，然后执行一次完整的 `ScrollVerifiedRowShiftAsync` 事务（不扫描、不 OCR）；
- 每轮写 `WHEEL_ANCHOR_PROBE_RESULT run, anchorRows, legacyDecision, legacyReason, agreement, wouldRescue, releaseSamples, detectMs`，结束写 `wheel-anchor-probe-result.json`；
- 控制台输出：`one_row_runs=`、`disagreement_runs=`、`would_rescue_runs=`、`legacy_failure_runs=`、`fallback_runs=`；
- 成功条件：shadow 模式 `one_row_runs == runs` 且 `disagreement == 0`；verify 模式所有轮次都以锚点证据提交一行。
