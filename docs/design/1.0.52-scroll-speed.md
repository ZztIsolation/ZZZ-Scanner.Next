## 1. 现状测量

数据来自 1.0.51 最终受控样本 `Experiments/selection-anchor/20261125/candidate-dxgi-4-controlled`（1920×1080，DXGI fast，200 件，用时 60.1s），逐事务从 `scan.log` 统计：

| 指标 | 数值 |
| --- | --- |
| 滚动事务次数 | 20（每次 1 行） |
| 发出滚轮 → 锚点首次唯一出现在目标行 | p50 **227ms**（205–265；含 40ms 悬停等待） |
| 发出滚轮 → 网格稳定（结构稳定期接受） | p50 **406ms**（264–429） |
| 发出滚轮 → 事务完成（含光标移开后 2 帧复核） | p50 **464ms**（353–485） |
| 事务完成 → 下一视口开始（`WaitForListStableAsync` + 行签名） | p50 **42ms** |
| 滚动后首格总耗时 / 同排普通面板等待 | 228ms / 178ms（滚动后首格多约 50ms） |
| 面板等待 | 平均 178ms × 198 件 ≈ 35s（约占 60%） |

每次推进的固定成本约 0.52s。200 件里滚动约占 10.4s（约 17%）；990 件约 106 次推进，约 55s。

一次事务内部的时间线（`fromTop=2`，事件 #249–#298）：

```
+0ms     ROW_SCROLL_TICK（随后光标悬停 40ms，发 -120）
+114ms   第一帧：列表尚未开始移动 → NoMove → 进入稳定期（无害，但不是真正的“没动”）
+128ms   开始移动；锚点变成 Weak/None（动画中途）
+221ms   锚点 Unique，已在目标行（分数 88→100）
+221–409ms 缓动尾段：列表仍在以 61→43→…→5→0 的帧差慢慢靠拢最后约 20px
+409ms   网格稳定（frameDistance ≤ 4），稳定期接受
+429/457ms 光标移开后连续 2 帧复核通过，事务完成
```

结论：

1. **单次事务的下限是游戏动画本身**，约 360–400ms（含缓动尾段）。在点击下一格之前必须等列表真正停稳，因为选中探针和面板证据都依赖静止画面，所以尾段不能省。单次事务最多再压缩约 50–80ms（重复的稳定确认和下一视口的重复等待）。
2. **主要节省空间来自减少事务次数**：一次推进多行，让多行共用一次动画尾段和确认开销。
3. 面板等待才是最大头（约 60%），但它是 1.0.47 起的安全门槛，不在本版范围内（§9）。

### 1.1 已有的游戏行为证据

1.0.51 采集（`Experiments/selection-anchor/20261125/gdi/…/click-r{1..4}-*.png`，列表顶部在第 2 行时）：点击视觉第 1、2、3、4 行第 1 列，前后网格平均差 1.7–1.9（不动）；第 4 行点击后最佳对齐位移只有 1px，属于选中态变化，不是滚动。也就是说，当前游戏中**点击第 4 行不会滚动**（与 F11 一致）。这是本版多行推进的前提，但样本只有一个位置和一列，需要 E0 扩大验证。

## 4. S1：事务内微调

只改锚点事务（verify/strict 且锚点可用），`off` 和回退事务保持 1.0.51 行为。

| 编号 | 改动 | 依据 | 预期 |
| --- | --- | --- | --- |
| S1-a | 锚点事务提交后，把复核阶段最后一帧的行签名直接作为下一视口的稳定证据：跳过下一轮循环开头的 `WaitForListStableAsync` 和重复的 `CaptureRowSignatures`，`OVERLAP_VIEWPORT` 仍照常记录 | 复核阶段已经要求连续 2 帧网格稳定；下一视口又等一次稳定，属于重复 | 约 40ms/次 |
| S1-b | 稳定期接受后立即抓第一帧复核，不再先等一个轮询间隔 | 稳定期最后一帧已经稳定 | 约 10–15ms/次 |
| S1-c | 第一帧采样推迟到发出滚轮后约 150ms（可配置），避免把“还没开始动”记成 `ROW_SCROLL_NO_MOVE_CONFIRMED` | 时间线中 +114ms 的 NoMove 是假信号，会让日志和 benchmark 的“未移动”计数失真 | 主要是诊断准确性，时间收益约 0 |
| S1-d | 在 `ROW_SCROLL_TIMING` 增加 `anchor_first_unique_ms`、`grid_stable_ms`、`release_ms` 字段，benchmark 输出对应统计 | 后续调参需要逐阶段耗时，目前只能从原始日志推算 | 无 |

刻度等待（悬停 40ms、`scrollTickDelayMs`）不改：1.0.46 已证明过早移开光标会让平滑滚动回弹。

## 5. S2：多行推进（主方案）

### 5.1 原理

当前每屏只扫 1 个新行（中部状态扫视觉第 2、3 行，但第 2 行在上一屏已扫过），然后推进 1 行。点击第 4 行不再滚动后，可以改为：

- **首屏**：扫第 1–4 行。
- **中部**：扫第 2–4 行（3 个新行）。最后点开的盘在第 4 行，以它为锚点，一次请求推进 **K = 3** 行，锚点应从第 4 行到第 1 行。新视口的第 2–4 行就是 3 个新行。
- **接近底部**：K = min(3, maxVisibleTop − 当前顶部)，锚点期望落在第 4 − K 行。
- **到底**：沿用 1.0.51 的观察到底路径（锚点不动 + 滑块到达轨道末端双帧）。

逻辑行仍按升序扫描，导出顺序与 1.0.51 相同，因此可以直接用导出逐项比对验证。

990 件（110 行）的推进次数从约 106 次降到约 36 次。

### 5.2 多行的输入方式（P0 决定选哪种）

| 方式 | 做法 | 估计耗时（3 行） | 风险 |
| --- | --- | --- | --- |
| A 链式 | 发 1 格 → 锚点首次出现在下一行（约 190ms）立即发下一格 → … → 最后一格后走完整的稳定与复核 | 40 + 3×190 + 尾段 180 + 复核 50 ≈ **0.84s** | 在缓动中途发输入可能被游戏合并或加速（1.0.50 `98b05f8` 的教训）。由于每一步都等锚点确认到达再发，越滚会被锚点发现 |
| B 连发 | 按固定间隔（候选 60/100/150ms）连发 K 格，然后一次稳定与复核；若锚点显示 k < K，再按链式逐格补足 | 若游戏把多格合成一次动画：40 + 200 + 约 360 + 50 ≈ **0.65s** | 游戏可能对连发限幅或合并（zzz-ddtool 文档明确提醒不要用放大的单个 delta 代替多事件） |

两种方式都**只认锚点行号**：最终要求锚点 Unique 且行号 = 4 − K，光标移开后连续 2 帧一致。任何越过目标（锚点离开视口或行号小于期望）都停止，不回滚。

### 5.3 判定规则（推广 1.0.51 的 `Reconcile`）

`SelectionAnchorAdvancePolicy.Reconcile` 现在只接受 0–2 行。新增 `ReconcileRows(structure, anchor, r0, requestedRows)`：

| 锚点结果 | 结构复核 | 结论 |
| --- | --- | --- |
| Unique，k = r0 − r1 = K | 不冲突 | 接受 K 行 |
| Unique，0 < k < K | 网格已停稳 | “未满”：链式补发剩余格数（每格都要锚点确认），补发上限 K 格 |
| Unique，k = 0 | 网格未动 | 沿用 1.0.51：刻度被吞，按原规则补发或进入观察到底 |
| Unique，k > K，或 None 且结构显示越过 | — | 越滚，停止 |
| Unique，k = K 但结构强证据冲突 | 冲突 | 停止 |
| Weak / Multiple / None（停稳后仍是） | — | verify：回退为 1.0.51 单行事务前先停止多行推进（见 5.5）；strict：停止 |

结构复核用 1.0.51 的真实行距卡片内部签名，比较“推进前第 K+1…4 行”与“推进后第 1…4−K 行”。K = 3 时只有 1 行重叠（推进前第 4 行 ↔ 推进后第 1 行），这一行正是锚点所在行，可作为强一致性检查。

### 5.4 需要同步修改的地方

| 位置 | 改动 |
| --- | --- |
| `BuildOverlapScanCandidates` | 多行模式下中部视口扫第 2–4 行，首屏扫第 1–4 行 |
| 新函数 `ScrollAnchorRowsAsync(requestedRows, inputMode)` | 独立实现多行事务；1.0.51 的 `ScrollVerifiedRowShiftAsync` 保持不变，继续服务 K = 1、`off` 与回退 |
| `VerifiedInventoryTraversal.Advance` | 由“rows == 1”改为“rows == requestedRows 且有锚点证据” |
| 日志 | `ROW_SCROLL_DONE`、`OVERLAP_SCROLL_ACCEPTED`、`WHEEL_ANCHOR_DECISION` 增加 `requestedRows=`；新增 `WHEEL_ANCHOR_STEP`（链式每一步）与 `WHEEL_ANCHOR_TOPUP`（补发） |
| `ScanBenchmark` | `NonUnitRowScrollDoneCount`、`strict_one_way_scroll`、`ReadAnchorVerifiedPositions`（目前要求 `toTop == fromTop + 1`）、`no_unsafe_visual_row2` 都改为“rowsAdvanced == requestedRows”；旧日志没有 `requestedRows` 字段时按 1 处理，保证 1.0.49/1.0.51 日志评估结果不变 |
| 配置 | profile `rowsPerAdvance`（P2 默认 1，P3 门禁通过后改 3）、`multiRowInput: chained|burst`；CLI `--rows-per-advance 1|2|3`、`--multi-row-input`；环境变量 `ZZZ_SCANNER_ROWS_PER_ADVANCE` 用于现场紧急退回 1 |
| `--wheel-anchor-probe` | 增加 `--rows K --multi-row-input chained|burst [--burst-interval-ms N]`，统计 k 分布、补发次数、耗时 |

### 5.5 回退规则

- 推进前锚点不在第 4 行（例如第 4 行全被筛选跳过、最后点的是第 3 行）：本次 K 降为 r0 − 1；r0 < 2 时先按 1.0.51 主动锚点规则点第 3 行最后一列，再以 K = 2 推进（不额外点击第 4 行）。
- 多行事务出现 Weak/Multiple/None 且网格已停稳：verify 下本次扫描剩余部分降级为 1.0.51 单行事务，并记录 `WHEEL_ANCHOR_MULTIROW_DISABLED reason=...`；不在同一事务内混用。
- 环境变量或 CLI 设为 1 时，行为与 1.0.51 完全相同（回归测试保证）。

| ID | 实验 | 方法 | 通过标准 / 决策 |
| --- | --- | --- | --- |
| E0 | 第 4 行（及首屏第 1 行）点击是否会滚动 | 扩展 `--selection-anchor-capture`：列表中部（顶部 ≥ 5）、接近底部两处，点击第 1–4 行 × 第 1、5、9 列，GDI/DXGI 各一次，三档分辨率 | 第 4 行所有点击网格位移 ≤ 2px。若第 4 行在某些位置会滚动，S2 不可行，只做 S1 |

| E2 | 连发 K = 3 | `--wheel-anchor-probe --rows 3 --multi-row-input burst --burst-interval-ms 60/100/150`，各 30 次，GDI/DXGI | 记录 k 分布与耗时；可用条件：30/30 最终 k = 3、无越滚、补发 ≤ 1 次/30 |
| E3 | 链式 K = 3 | `--rows 3 --multi-row-input chained`，30 次，GDI/DXGI | 同上 |
| E4 | 深列表连续推进 | E2/E3 中较好的一种加 `--continuous`，覆盖到底部 | 无越滚；到底时 K 正确缩小，观察到底路径正常 |

## 8. 风险

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 某些位置点击第 4 行会自动滚动（zzz-ddtool 游戏规则 G03 记录过“首/末行可能使焦点自动居中”） | 多行模式下扫第 4 行时视口错位 | E0 先验证；扫第 4 行每格后可选检查网格是否位移（复用面板目标证据中的选中探针），位移即停止 |
| 游戏对连发或缓动中途的输入合并、加速 | 越滚 | 只认锚点行号，越过目标即停止；E2/E3 量化 |
| 锚点在第 4 行时离列表下边缘近，部分环境被裁切 | 基线不可用 | 1080p 下第 4 行采样段到 y≈836，`listGridRect` 下沿 892，有余量；其他分辨率在 E0 中确认 |
| 推进次数减少后，每屏连续扫 3 行，OCR 积压变化 | 吞吐变化 | 当前 `ocr_backlog_max=2`，余量充足；P3 记录 backlog |
| benchmark 门禁推广出错，误放行或误拦截 | 验收失真 | 用 1.0.49、1.0.51 的真实日志做回归，评估结果必须不变 |
| 期望收益被跨日环境波动掩盖 | 结论不可信 | 只用同日同起点 A/B（沿用 1.0.51 PERFORMANCE 的方法） |

## 9. 不在本版范围

- **面板等待**（约 60% 耗时）：120ms 下限与稳定帧是 1.0.47 为防止旧面板重复导出设立的安全门槛。若要优化，需要单独立项（例如在锚点给出可靠位置后，研究同排点击能否以“选中框已移到目标格 + 面板文字变化”替代部分固定等待），并做完整的重复导出风险评估。
- 删除旧的 `NativeEdgeClick` 代码与 `--edge-scroll-probe`：可以在 1.0.52 顺带做，但不与本优化放在同一提交。
- 1.0.51 未专项验收的环境（HDR、非 96 DPI、1440p/4K、云端）：按 1.0.51 设计 §19.3 补测；S2 上线前，这些环境至少要完成 E0。
