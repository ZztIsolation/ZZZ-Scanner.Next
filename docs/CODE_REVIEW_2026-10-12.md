## 当前扫描实现

### 从窗口到导出的处理链路

```text
定位游戏窗口并读取客户区
    → 标题 OCR、画面健康和仓库结构预检
    → 独立画面的仓库数量共识
    → 安装输入守卫并回到列表顶部
    → 按逻辑行规划可访问格子
    → 判断品质并按需点击
    → 验证目标选中、详情变化、稳定性和 ROI 完整度
    → 截图进入有界队列
    → 多个 OCR worker 并行识别与清洗
    → 结果按采集索引顺序提交
    → 完整导出或部分导出
```

| 阶段 | 实现 | 主要依赖 |
| --- | --- | --- |
| 窗口定位 | 按进程名查找主窗口，读取客户区 | 进程名、窗口几何与显示环境 |
| 坐标换算 | 将标准布局中的归一化坐标映射到客户区 | 已适配的仓库布局 |
| 仓库确认 | 标题语义、灰度结构、画面健康、连续帧门禁 | 可见且可读的仓库界面 |
| 数量确认 | 多次独立截图中出现两次一致结果 | 数量 OCR；一致结果仍可能有系统性误差 |
| 回顶 | 滚动条探针、有界滚轮、必要时拖动滑块 | 滚动条位置与可见性 |
| 详情读取 | 固定 ROI、文本变化、选中状态和稳定帧 | 点击与面板内容的对应关系 |
| OCR | PP-OCRv5，部分字段可由 Fast OCR 模板替代 | 模型、词典、精确视觉配置 |
| 清洗 | 文本匹配、数值规则、槽位检查 | 领域约束及纠错接受边界 |

它通过固定布局坐标访问格子，没有通过目标检测逐个寻找驱动盘，也没有取得游戏内部物品标识。因此，正确性依赖“逻辑位置与实际位置一致”和“当前详情属于目标格”两个条件。

### 下一项和下一行定位

内置配置为 4 个视觉行、9 列。同一行内按列递增，点击点由 `driveDiscOffset + driveDiscStep × 行列编号` 计算，再映射到屏幕。相关入口为 [ScanVisualRowAsync](../Scanning/ScanController.cs)，基线第 1614 行。

仓库数量用于计算总行数及末行列数。`BuildOverlapScanCandidates` 采用下列访问策略，并跳过已登记的逻辑行：

| 列表位置 | 候选视觉行 |
| --- | --- |
| 顶部且尚未到底 | 第 1、2、3 行 |
| 中间 | 第 2、3 行 |
| 底部 | 第 2、3、4 行 |
| 全部物品不超过一屏 | 第 1 至第 4 行中实际存在的行 |

1.0.49 默认使用 `NativeEdgeClick`：点击视觉第 4 行第 1 列，利用游戏原生行为推进列表；随后点击第 2 行末列，将选择态移离待扫行。中间推进后通常只需采集新进入视觉第 3 行的逻辑行。

列表稳定且发生变化时，当前代码直接提交一行；稳定但未观察到变化时，重新采集视觉第 3 行并比较详情／格子指纹。REV-001 和 REV-005 分别约束这两条提交路径。

旧 `WheelVerified` 保留了零行／一行／两行结构比较、滚动条辅助和鼠标移开后的再次确认。可参考 [ScrollVerifiedRowShiftAsync](../Scanning/ScanController.cs)，基线第 2621 行，将输入方式与位移验证解耦。

### 应保留的稳定性机制

- 仓库预检在输入前结合标题与结构，避免单一颜色决定页面身份。
- 回顶与滚动恢复有边界，避免无限输入。
- 首对驱动盘建立切换与返回基线，相同内容盘允许额外邻格往返验证。
- 普通采集结合目标选择态、文本稳定性和可见 ROI 布局。
- 可变副词条布局支持短 ROI 列表，短布局至少连续三帧确认。
- OCR 结果按索引提交，避免 worker 完成顺序改变扫描顺序。
- 导航失败可排空已采集 OCR，保留部分结果。
- 截图协调器串行管理捕获源，避免共享 DXGI 对象的并发访问。

连续采样相似不必然意味着观察到了不同的游戏渲染帧，GDI 尤其可能重复读取同一显示帧。最低等待时间也是安全条件，性能优化不能只减少稳定帧数或等待时间。

## 正确性与稳定性整改项

### REV-001 原生行推进缺少最终位移证明

**优先级：P1。状态：待修复。**

位置：[ScanController.cs](../Scanning/ScanController.cs)，`AdvanceNativeEdgeClickAsync`，基线第 2195 行；[NativeEdgeClick.cs](../Scanning/NativeEdgeClick.cs)，`ResolveSettle`，第 36 行。

`sawMovement |= currentMovementDistance > ListMovementTolerance` 会锁存任意中间帧的变化。后续只要连续采样稳定，就返回 `Changed=true`。最终画面即使回到初始位置，也不撤销这项证据；接受路径不区分半行、一行或多行位移，直接增加逻辑顶部行号。

合成输入中，设置 `Settled=true`、`Changed=true`，并让前后列表哈希相同，策略仍返回 `AdvanceAssumedOne`。这验证了策略缺口，不代表本轮已在真实游戏中复现回弹。

**影响：**实际列表位置与逻辑行号可能脱节，出现重扫、漏扫或后续保护停止。逻辑行集合只记录程序分配的行号，不能独立证明物理覆盖率。

**修复方向：**以最终稳定位置提交位移；复用零／一／两行结构比较及滚动条证据。原生点击保留为输入方式，位移判断独立于输入方式。无法消歧时重试或停止，不靠自增计数补齐覆盖率。

**验收条件：**

- [ ] 无移动、仅高亮变化、瞬时变化后回到基线都不能提交一行。
- [ ] 半行停顿与两行越界不能提交一行。
- [ ] 延迟开始的正常一行移动可在有界等待内正确接受。
- [ ] 真机导出与基准物品集合一致；允许合法同属性盘，不能只用“内容重复数为零”判断正确。
- [ ] 推进日志记录最终证据、候选位移和接受／拒绝原因。

### REV-002 OCR 管线缺少统一故障传播

**优先级：P1。状态：待修复。**

位置：[ScanController.cs](../Scanning/ScanController.cs)，`ConsumeOcrWorker` 第 5018 行、`ConsumeOcrResults` 第 5118 行、`ScanAsync` 第 354 行。

结果消费者写诊断文件或处理进度时可能抛异常，但没有统一通知其余阶段。worker 的 `ocrResults.Add(...)` 没有取消令牌；会话先等待所有 worker，然后才等待结果消费者。

消费者退出后，结果队列可能塞满，使 worker 阻塞；截图队列随后也可能塞满。即使用户取消使生产者退出，收尾仍可能等待被阻塞的 worker。

离线故障注入使用一个普通文件作为输出目录，实际结果为消费者抛出 `DirectoryNotFoundException`，关联取消源仍未取消；容量为 1 的结果队列继续写入后，下一次限时写入失败。整条扫描的永久等待结论来自这一阻塞条件与收尾顺序，没有运行真实游戏故障注入。

**修复方向：**统一管理生产者、worker 和结果消费者的生命周期。任一阶段失败立即传播故障；所有队列等待可被终止。明确区分采集失败后排空已有工作与管线自身损坏后中止。worker 初始化失败也必须及时传播。注意失败退出时仍需释放剩余 Bitmap，保留已提交结果。

**验收条件：**

- [ ] 结果消费者写文件失败、进度处理失败后，其他阶段在约定超时内退出。
- [ ] worker 模型初始化失败不会让截图生产者无限等待。
- [ ] 截图队列和结果队列满时，取消均能结束任务。
- [ ] 正常导航失败仍可按策略排空已采集 OCR。
- [ ] Bitmap 所有权转移与释放完整，无重复释放或遗留队列。
- [ ] 终态保留最初失败原因，并且只发送一次。

### REV-003 空 OCR 副词条被当作不存在

**优先级：P1。状态：待修复。**

位置：[DriveDiscCleaner.cs](../Cleaning/DriveDiscCleaner.cs)，`Clean`，基线第 65 至 77 行。

已传入的副词条名称或值为空时，代码执行 `break`，跳出的是 `switch`。后面的词条仍继续处理，最后返回成功。完整 12 ROI 输入中，第一个副词条值为空，实际导出只包含后面三条，且没有清洗异常。

**影响：**静默丢失属性，失败数仍为零，也不会触发依赖清洗异常的 OCR 重试。奇数 ROI 的半对词条同样可能被忽略。

**修复方向：**由采集端确认合法短布局。对已传入的每个副词条对，名称或值为空都必须重识别或失败；清洗器拒绝半对输入和中间断层，不能凭 OCR 空文本重新缩短布局。

**验收条件：**

- [ ] 合法的 4、6、8、10、12 个 ROI 可正常处理。
- [ ] 已捕获词条任意一侧为空时，不产生缺字段的成功导出。
- [ ] 奇数数量 ROI、中间缺失和断层有明确错误。
- [ ] 重试成功与失败分别计入正确终态，保留诊断信息。

### REV-004 属性类型和等级数值约束不完整

**优先级：P2。状态：待修复。**

位置：[DriveDiscCleaner.cs](../Cleaning/DriveDiscCleaner.cs)，`CleanStatValue` 第 169 行、`CandidateValueKeys` 第 236 行；[DriveDiscSlotSafety.cs](../Cleaning/DriveDiscSlotSafety.cs)，第 46 行。

`forceMainPercent` 只把百分比候选放到前面，仍允许固定数值候选凭相似度获胜。最终数值专项检查主要覆盖 1 至 3 号位，未完整约束其他槽位的类型和等级对应值。

| 离线输入 | 实际输出 | 与当前项目规则的冲突 |
| --- | --- | --- |
| S、4 号位、15/15、生命值 550 | 固定生命值 550，成功 | 该槽位生命值主属性应为百分比 |
| S、4 号位、15/15、暴击率 6% | 暴击率 6%，成功 | 项目数据中满级应为 24% |
| 两条攻击力 19 副词条 | 两条均保留，成功 | 缺少同类型重复副词条检查 |

**修复方向：**先按品质、槽位、等级、属性和数值类型确定合法集合，再执行 OCR 纠错。强制百分比时排除固定值候选。补充最终领域校验；副词条判重须区分固定值与百分比，例如固定攻击力和攻击力百分比不能仅因名称相同而误判重复。

**验收条件：**

- [ ] 4 至 6 号位的生命／攻击／防御主属性不能导出固定值。
- [ ] 主属性值与品质、等级一致，覆盖低等级及满级。
- [ ] 错误值不能仅因模糊匹配而越过类型约束。
- [ ] 同类型重复副词条被拒绝，合法固定值／百分比组合仍可导出。
- [ ] 数值精度与项目规则保持一致，合法样本不被过度拒绝。

### REV-005 行哈希兜底无法证明一行位移

**优先级：P2。状态：待修复。**

位置：[NativeEdgeClick.cs](../Scanning/NativeEdgeClick.cs)，`ResolveFallback` 第 41 行、`DetailPanelFingerprint.Compute` 第 195 行。

稳定但没有观察到列表变化时，重新采集视觉第 3 行。哈希相同被解释为到底，不同被解释为前进一行。详情采样虽做四位亮度量化，但最终为严格哈希相等。

合成图像仅将一个采样像素灰度从 15 改为 16，哈希即不同，策略返回 `AdvanceAssumedOne`。相同内容受渲染噪声影响可能产生差异；两个不同物理行也可能内容相同。两种情况都不能仅凭内容哈希证明位置。

**修复方向：**将哈希降为辅助证据，使用可度量距离、重复观测和列表／滚动条位置验证。与 REV-001 使用统一位移提交契约；不要把未知状态强行分为“到底”和“前进一行”。

**验收条件：**

- [ ] 微小亮度扰动、采样像素跨量化边界不直接产生一行提交。
- [ ] 两个内容相同的物理行不直接被判为到底。
- [ ] 品质筛选跳过行的格子指纹也遵循同样的保守规则。
- [ ] 缓冲行只有在位移证据成立后入队；拒绝路径释放图片且不提前计数。

### REV-006 名称匹配失败仍作为成功结果

**优先级：P2。状态：待修复。**

位置：[DriveDiscCleaner.cs](../Cleaning/DriveDiscCleaner.cs)，`CleanName` 第 102 行；[StringMatcher.cs](../Cleaning/StringMatcher.cs)，`BestMatch` 第 33 行。

匹配分数不足时 `BestMatch` 返回原始文本，`CleanName` 不检查是否命中词典，最终槽位校验也不检查套装名称。离线输入 `[4]` 成功导出空名称，`未知套装[4]` 成功导出未知名称。

**修复方向：**显式区分接受匹配与未命中，校验套装词典成员身份及匹配可信度。未知新套装保留原文和诊断，但不伪装成正常识别结果。不要把“总能返回字符串”当作“识别成功”。

**验收条件：**

### REV-007 扫描互斥没有覆盖所有入口

**优先级：P2。状态：待修复。**

位置：[Program.cs](../Program.cs)，CLI Mutex 第 428 行；[MainForm.cs](../Ui/MainForm.cs)，第 344 行；[WebSocketHost.cs](../WebSocket/WebSocketHost.cs)，实例内 `_scanGate` 第 18 行。

**验收条件：**

- [ ] GUI＋GUI、GUI＋CLI、GUI＋WebSocket、扫描＋探针组合均只允许一个输入执行者。
- [ ] 第二个实例在任何点击或滚动前收到明确 busy 状态。
- [ ] 正常完成、异常和进程退出后可重新开始扫描。

### REV-009 后端降级没有同步重建采集时序

**优先级：P2。状态：待修复。**

## 性能分析与优化候选

以下项目不应通过放松正确性门槛换取速度。整盘收益需要在相同库存、分辨率、后端和配置下测量。

### 交互等待与 OCR 并行关系

默认普通 GDI 面板采集先等待约 40ms，再进入至少 180ms 的接受计时，仅该部分约 220ms。默认 DXGI 对应约 40ms 加 120ms。这不是每盘完整耗时，还需包含品质探测、输入守卫、选择态截图、行推进、排队及重试。

```text
总耗时约等于 启动与回顶 + max(采集总耗时, OCR 总耗时) + 收尾
```

高性能默认在处理器数量足够时使用两个 OCR worker，并保留一个预检／仓库守卫识别器，即约三个模型会话。OCR 没有积压时，继续加 worker 未必提升吞吐，反而增加线程和模型开销。

### PERF-001 预解码 Fast OCR 模板特征

**状态：待评估。证据：局部微基准。**

位置：[FastOcrTemplateIndex.cs](../Ocr/FastOcrTemplateIndex.cs)，第 228、260、895 行。

每次比较模板都重新调用 `FromHexWords(template.Bits)`，解析不可变十六进制字符串并分配数组。可在索引加载时预解码，之后复用不可变特征。

基线微基准使用仓库内 `cloud-1920x1080-current` 的 `subStat1` 共 360 个模板，以首个模板为查询特征，各预热 20 轮，再各执行 500 轮距离比较；使用 `Stopwatch` 和 `GC.GetAllocatedBytesForCurrentThread` 计量。预解码成本不包含在缓存路径内循环中。

| 距离比较内循环 | 耗时 | 当前线程托管分配 |
| --- | --- | --- |
| 每次解析模板 | 196.38ms | 67.29 MiB |
| 预解码后复用 | 19.54ms | 约 0 MiB |

该结果只证明距离比较内循环存在优化空间，未包括图像特征提取、OCR 推理和界面操作，不代表整盘加速十倍。

验收应确认匹配标签、分数、第二候选和接受决策一致，检查并发只读安全，并记录索引加载成本、常驻内存及整盘收益。

### PERF-002 按图片字节预算限制队列

**状态：待评估。证据：容量估算。**

位置：[ScanController.cs](../Scanning/ScanController.cs)，队列容量第 103 行；[scan_profiles.json](../Data/scan_profiles.json)，详情面板坐标。

| 分辨率 | 单张详情图 | 默认 48 张队列 |
| --- | --- | --- |
| 1920×1080 | 约 0.89 MiB | 约 42.6 MiB |

4K、256 张时仅图片数据约 909 MiB；这些数值不含模型、推理张量、worker 当前批次、截图缓冲和调试图，也不构成 4K 真机兼容性验证。

可按分辨率与图片字节数动态限制排队量，保持背压，避免把增大队列作为默认加速方式。验收记录吞吐、队列 P95／最大长度、进程私有内存和取消延迟。

### PERF-003 减少截图与预处理缓冲创建

**状态：待评估。证据：代码路径。**

**状态：待评估。证据：代码路径。**

`PanelStabilityMode.Panel` 下仍计算文本核心稳定性，正常接受路径使用文本核心计数。应检查配置、实现与日志的对应关系，明确 Panel、TextCore、Auto 各自控制哪些判断，再决定是否消除重复计算。
