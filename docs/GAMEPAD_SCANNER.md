## 当前整改：只替换选盘输入

前一版不只替换了输入：还把验证工具的逐件三次整屏观察、网格/详情稳定检查及额外等待搬入正式生产者。这超出了用户要求，造成重复判稳。下方历史记录描述该旧实现，不能作为当前版本的验收结果。

当前正式数据通路：原仓库预检及库存数量共识 → 起点网格标定、右移准备邻盘基线 → 原 ScanVisualRowAsync 回首件采集 → 输入适配器选盘 → 原 CaptureStablePanelWithRetryAsync / CaptureStablePanelAsync → 原有界截图队列 → 原 OCR、清洗、序号排序和导出。准备成功的手柄首格不再另跑独立首两件往返；原详情接受门槛不变。

正式扫描不再调用 GridTraversal 或 GamepadCaptureSink。GridTraversal 保留给独立验证工具使用。输入适配器不读取详情、不执行 OCR、不创建另一套入队规则。

| 项目 | 当前处理 |
| --- | --- |
| 正常同排下一件 | 一次 D-pad Right，然后进入原版详情采集；不逐件截图整屏识别网格 |
| 首件与品质筛选跳格 | 正常手柄首件复用启动邻盘基线，消除独立首对往返；不满足准备条件时沿用原首对与筛选路径 |
| 已在目标格 | 不发送方向 |
| 行尾及末行不足 | 根据该行实际格数回首列，下移后证明只前进一行 |
| 动态网格 | 仅起点、行边界和异常恢复时观察；更新原品质/选中探针坐标，详情 ROI 仍用原 profile |
| 详情判稳与重试 | 原函数、原参数、原接受门槛；原高级设置重新对手柄生效 |
| 普通单件 OCR / 清洗失败 | 原消费者记录错误、计入 Failed 并继续；保留原部分结果导出语义 |
| 重复保护 | 撤掉 ControllerGrid 绕过逻辑，恢复原 ChangedText / IdenticalNeighborRoundTrip 证据规则 |
| 取消、未满级停止、错误收尾 | 保留原业务处理；方向输入在取消、失焦或异常时释放 |

鼠标底行点击和 D-pad Down 引发滚动的时机不等价，因此换行导航仍需独立适配；逐件采集和 OCR 不另建实现。换行前保存原详情基线传给下一行，避免下移后把当前盘误作“上一件”。异常重试时重读实际焦点，避免按丢输入后的推测坐标继续移动。网格确认需要至少两张稳定图，但只发生在上述导航边界，不是每件盘执行。

此前增加的 worker/消费者顶层故障取消传播和残留截图释放仍保留，属于资源/故障修复。它们不改变普通 OCR 失败继续的规则，也不是提速手段；整个工作区不能描述成相对原仓库只有一行点击变化。

### 性能口径

旧路径 18 件采集 14.583 秒，约 74 件/分钟。用户提供的原鼠标基线约 150 件/分钟，即 400 ms/件；这不是本轮重新测得的鼠标结果。

旧路径另一轮 18 件的主要累计开销：60 次整屏捕获约 4.03 秒、网格分析 1.40 秒、详情签名 0.96 秒、观察间等待 1.52 秒、方向按压及固定间隔 3.35 秒、额外详情等待 1.76 秒。这些统计不能直接相加预测新版本速度。

当前按压暂保留 60 ms，取消每件固定 100 ms 释放等待及验证工具的额外 180 ms 详情等待。相邻输入至少释放 40 ms，从上次释放开始计时，原详情采集通常已覆盖它；仅紧邻多步输入补足剩余时间。原详情稳定等待全部保留，没有通过降低门槛提速。

可通过 CLI `--gamepad-hold-ms 50` 或 `40` 单独设置实验按压时长（范围 20–100 ms，默认仍为 60 ms）。本机前 5 行 / 45 件实测：50 ms 采集 18.351 秒，40 ms 采集 18.448 秒，两档均 OCR 45 成功、0 失败、无邻盘重试，45 件及 540 字段与 60 ms 基线一致。40 ms 暂未测得额外收益，尚不据此更改默认值；详见 [逐档实验](GAMEPAD_FULL_SCAN_2026-10-21.md#按压时长逐档实验前-5-行--45-件)。

原扫描器已经重叠 OCR 与导航。坐标计算开销很小，手柄不保证必然比鼠标更快；应以同起点、同 OCR/截图配置、同一批盘的实测决定。保留原 CELL_TIMING，新增 GAMEPAD_INPUT_ONLY、GAMEPAD_ROW_DONE、GAMEPAD_ROW_ADVANCE、GAMEPAD_CAPTURE_DONE 日志，区分逐件采集与导航边界开销。

## 替换范围

GUI 默认项、CLI `--scan-once` 和 WebSocket 未指定遍历模式的扫描请求，均通过 `FromProfile → Gamepad` 进入手柄导航。不会再执行驱动盘页签点击、鼠标归顶、逐格点击或旧换行流程。旧遍历算法保留在显式回归选项中，手柄失败时不会自动切换回鼠标。

开始前需要打开背包驱动盘页，并选中整个背包第一个盘。正式扫描器先做原有仓库识别和数量共识检查，再验证动态网格、首行首列及滚动条顶部；整份库存已完整显示在当前网格内时不要求存在滚动条。无法确认顶部就停止，不使用连续上移归顶，因为游戏可能纵向循环。

共享实现位于 `Scanning/Gamepad/`；独立验证工具通过源码链接复用同一套设备、网格、稳定观察和遍历策略。正式适配器是 `Scanning/ScanController.Gamepad.cs`。验证工具的串行 OCR 模式继续用于历史基线对照，不是正式扫描器的处理路径。

## 正式数据通路

1. 截图后动态识别列数、当前行实际格数和选中框。连续 3 次位置、整屏行特征、详情字段特征及副词条数量边界稳定，才接受当前格。
2. 使用原扫描配置的详情区域、12 个字段区域及 `EvaluateVisibleRois`，保留 0–4 条连续副词条处理。稀有度从当前选中格品质条识别，按原筛选选项决定是否提交。
3. 将接受画面中的详情区域复制成独立 Bitmap，赋予连续 OCR 序号，提交原有有界 `BlockingCollection<DiscCapture>`。访问位置计数与 OCR 序号分离，被品质筛选跳过的位置不制造 OCR 序号空洞。
4. 提交成功后立即继续导航。原 `StartOcrWorkers` 在后台完成 PP-OCR、清洗、规则校验、亮度重试及可选 Fast OCR / 影子数据处理。
5. 原 `ConsumeOcrResults` 使用 `SortedDictionary` 消化乱序结果；导出仍按 `Index` 排序，JSON 字段格式不变。单件失败也推进结果序号，不阻塞其后的成功结果。

默认手柄时序：D-pad 按压 60 ms、释放间隔 100 ms、观察轮询 30 ms；详情最小释放后等待仍为 180 ms。当前只重叠 OCR 与导航，没有进一步降低稳定性门槛。GDI / DXGI 截图选项继续走正式扫描器后端；本次实测为 GDI。

每行先逐格右移，末格右移回首列后下移；末行不满时使用该行实际格数。每次位移必须满足几何和行特征规则，不能根据 OCR 内容不同来猜测移动成功。首次右移稳定不动仅重试一次。滚动必须确认一行重叠，跳列、跳行、签名歧义都会停止。全量结束仍需独立库存数量与底部/绕回证据一致；达到用户读取上限则直接结束采集，不再额外移动。

## 错误与停止策略

| 情况 | 行为 |
| --- | --- |
| 普通单件 OCR / 清洗失败 | 记录 `NNNN.error.txt`、增加 Failed，继续导航和后续识别；最终输出 `export.partial.json` |
| 两件或多件盘属性完全相同 | 在 `ControllerGrid` 几何确认下保留全部结果，不按 OCR 指纹去重或触发旧重复保护 |
| 导航不明确、详情边界不稳定、失焦或窗口几何变化 | 停止输入并归零，按原捕获失败策略处理已经入队的截图，输出部分结果及失败原因 |
| 用户取消 | 停止输入，按原取消策略丢弃待处理截图，不继续移动 |
| 检测到非 15 级且启用了原停止选项 | 按排序后的序号停止，之后的结果不导出；保留原有停止语义 |
| OCR worker 初始化/顶层异常，或结果消费者退出 | 取消生产管线，解除有界队列等待，结束任务后释放残留截图；不当作普通单件错误继续无限扫描 |
| 缺少或无法使用驱动 | 返回 `gamepad_driver_unavailable`；GUI 可打开安装引导，不自动安装或覆盖驱动 |

普通单件 OCR 失败继续的行为来自原正式消费者；未将验证工具的“识别失败立即停”策略迁入正式路径。导航证明只绑定稳定画面的具体位置，不能证明 OCR 语义一定正确；原清洗器的名称映射边界等审查问题仍保留。

队列满时每 50 ms 检查取消/前台状态。输入按压阶段每 10 ms 检查取消/前台状态，并在 `finally` 中释放。新构建的扫描器与验证工具共用虚拟设备互斥信号量，避免两者同时发送报告。旧版本工具仍应关闭。

## 驱动和权限

固定客户端 `Nefarius.ViGEm.Client 1.21.256`；安装器 `1.22.0` 对应内核驱动 `1.21.442.0`。沿用原检测、安装器 SHA-256 校验及安装引导。已有其他版本标记为未验证，不自动覆盖。ViGEmBus 已停止维护，多电脑适配仍需要实测。

手柄路径不再要求游戏与扫描器拥有相同的鼠标注入权限：它使用桌面截图和 ViGEm 报告；前台、窗口几何和截图有效性检查仍执行。旧鼠标路径继续保留原权限检查。首次安装内核驱动仍由官方安装器请求 UAC。
