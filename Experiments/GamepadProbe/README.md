# 手柄导航验证工具

这是独立的 WinForms 实验程序，用虚拟 Xbox 360 手柄验证绝区零「背包 → 驱动盘」的导航行为。0.3.1 提供动态网格与逐行遍历；**0.4.0 接入现有 PP-OCRv5、驱动盘清洗校验及分阶段性能记录**。它不依赖实体手柄，不发送键盘方向键，也不把发送次数当作物品 index。

本次实现复用 **ViGEmBus 内核驱动 + Nefarius.ViGEm.Client 1.21.256**，新增的是虚拟设备控制程序，没有编写或安装新的内核驱动。主扫描器只增加实验目录的编译排除，不引入该 NuGet 依赖、不修改扫描逻辑。

## 环境与启动

- Windows x64。ZIP 自带 .NET 8.0.32、ONNX Runtime 1.23.1、固定 OCR 模型和 app-local VC Runtime 14.44.35211.0；从源码开发仍需 .NET 8 SDK。
- 已安装且运行的 ViGEmBus 驱动；普通 Xbox 实体手柄的 USB 驱动不能替代它。
- 不需要购买或插入实体手柄。
- 一个工具实例只创建一个虚拟手柄。请勿同时运行正式扫描器或其他自动输入程序。

在仓库根目录构建：

```powershell
dotnet build Experiments/GamepadProbe/GamepadProbe.csproj -c Release
```

然后运行：

```text
Experiments/GamepadProbe/bin/Release/net8.0-windows/ZZZ.GamepadProbe.exe
```

本机已检测到签名有效、正在运行的 `Nefarius Virtual Gamepad Emulation Bus`，驱动版本 `1.21.442.0`，本次未安装或修改驱动。

没有驱动的机器可以点击「驱动安装引导」运行随包的官方安装器；只有用户点击后才请求管理员权限，不静默安装。启动时自动读取驱动文件版本和服务状态，区分未安装、基准版本、其他版本、未运行和未知。其他版本不自动覆盖，未知状态也不当作未安装。ViGEmBus 已退役，固定版本不等于已经完成长期兼容验证。

## 首次验证

1. 拔掉实体手柄，启动工具，确认驱动检测与「设备自检」通过，再点击「连接虚拟 Xbox 手柄」。虚拟设备在连接期间保持存在。若提示未安装，先使用安装引导并按要求重启。
2. 在游戏内启用手柄操作并进入背包的驱动盘页面。如果游戏没有自动切换，请手动检查游戏的输入设备设置。
3. 回到工具，确认进程名为 `ZenlessZoneZero`，勾选「已进入背包驱动盘页，启用方向输入」。程序绑定当前唯一游戏窗口所属进程。
4. 初始参数：D-pad、按压 80ms、释放间隔 350ms、次数 1。这是实验起点，不是已验证的游戏时序。
5. 点击工具中的方向按钮，在 3 秒倒计时内切回游戏，观察是否每次只移动一格或一行。用户实测绝区零的输入热切换会被功能键触发，0.2.0 已删除普通方向热键。
6. 如 D-pad 无效，停止并回到工具，将输入改为「左摇杆」，重新启用后再试。每次摇杆脉冲幅度为 ±24000，结束后回中。
7. 任意时刻 F10 停止、释放所有输入并解除启用。停止后必须重新勾选才能继续。

方向按钮等待 3 秒，供用户切回游戏，然后按「次数」发送同一方向。F10 仅用于紧急停止，可能触发游戏切回键鼠模式，不作为正常导航的一部分。

输入期间游戏失焦或退出会中止序列；每次等待最多约 10ms 检查一次前台进程（实际响应受系统调度影响）。取消、发送异常、日志异常和窗口关闭均有释放路径。设备与应用崩溃、系统挂起等极端场景仍需单独验证，不能将异步软件定时器视为硬实时保证。

工具不发送确认、返回、强化、删除等按键。起点需要用户手动选择；自动模式会视觉验证右移、回到首列及下移，不自动归位。

## 0.3.1 动态网格与自动遍历

### 操作步骤

1. 手动回到整个背包第一个盘，连接手柄并启用方向输入。
2. 点击「识别网格预览」，3 秒内切回游戏。确认青色格子未漏检、紫色框对应当前选中盘。
3. 默认搜索区域是客户区的 `2.5%,17%,68%,67%`（左、上、宽、高）。区域不正确时可调整；该参数不指定列数和格子尺寸。
4. 勾选起点确认。可手动输入页面显示的总盘数；这个值只作独立核对，不通过 OCR 获取。
5. 首次将「验证行数」设为 2～5，点击自动遍历。通过后重新回到起点，设为 0 测试完整背包。
6. 运行期间保持游戏前台，不手动操作、不切换排序/筛选、不改变窗口或分辨率。F10 或切出游戏可中止。

### 实现与约束

- GDI 截取游戏客户区，检查进程前台状态和窗口几何；位置或分辨率变化立即停止。
- 图像最长分析宽度为 1440，检测高饱和度连通区域，通过三侧边框覆盖与空心形状寻找选中框，再利用品质色条聚类得到行列中心和间距。不是通用物体检测模型，依赖目前游戏的彩色边框/品质条视觉特征。
- 不固定列数。实际 3840×2160 起始截图识别为 9 列、4 行，选中位置为 (0,0)。合成测试另覆盖 7、9、10、12 列，不能把缩放或合成测试等同于不同机器实测。
- 连续三次、间隔至少约 100ms 的观测一致才接受稳定状态；GDI 无渲染帧编号，这不是“三个不同游戏渲染帧”的保证。
- 0.3.1 支持头像／槽位角标截断的细选中框，排除其顶部碎片形成的假行。行内容采样锚定静止的品质条并使用局部灰度均值，避免选中框呼吸动画、亚像素位移造成假变化。
- 每次只发送一个方向脉冲。右移必须确认恰好下一列；末列回首列时不重复计数。只有一个盘的行根据视觉布局处理，不以右移不动证明循环。
- 起步的首次右移若稳定观测为未移动，额外等待 350ms 后只重试一次，兼容第一次输入仅切换手柄模式的情况；不增加访问数，重试后跳格或仍无移动会停止。
- 普通下移检查焦点下移一行；自动滚动时匹配至少两行重叠内容，要求最佳位移明确且与焦点变化共同推导出逻辑位移一行。跳列、跳行、相同行内容歧义、漏检和黑屏停止。
- 末行首列下移无变化时，允许第二次有释放间隔的探测。仍无变化且下方没有可见行，才报告底部候选；人工总数不符会报错。没有独立总数时不会宣称完整遍历成功。
- 同时支持末行下移绕回首行：比较起始整屏网格内容、焦点和布局；人工总数不符则停止，无独立总数只报告回到起点的候选。相似整屏内容仍可能造成歧义，不能仅靠图像匹配声称物品唯一性。
- 默认最多访问 5000 个位置、发送 15000 次指令。行数限制可提前结束短程实验。数量表示视觉确认的位置，不是 OCR 物品身份或物品去重数量。
- 保存初始/最终标注图、行边界及下移前后截图、JSONL 事件、参数和汇总。普通证据截图缩到最多 1280 宽，最多 600 张；初始/最终和识别失败图保留原分辨率。

### 结果与证据

输出目录：`%LOCALAPPDATA%\ZZZ-Scanner.Next\GamepadProbe\grid-时间戳`。

| summary.json Outcome | 含义 |
| --- | --- |
| ProbeLimitReached | 达到用户设置的验证行数，未完成整包验证 |
| CompletedWithExpectedCount | 访问数与人工总数一致，末行两次下移不动或纵向绕回初始网格 |
| BottomCandidate | 无独立总数的底部候选，仍需人工检查 |
| WrappedToStartCandidate | 无独立总数，观察到下移绕回初始网格，仍需人工检查 |
| StoppedAmbiguous | 网格、位置、行位移或计数有歧义，已停止 |
| Canceled | 用户中止 |

`events.jsonl` 包含 VISIT、MOVE、ROW_COMPLETE、ERROR、STARTUP_RETRY、RETURNED_TO_START；MOVE 记录前后完整网格观测、行签名、位移判定和匹配差异。检测未稳定时保存 `last-detection-failure.png`，便于排查 HDR、色条、框选样式等差异。截图可能包含 UID 和背包内容，不会自动上传，也不纳入发布包。

开发诊断：`--analyze-grid <截图> <输出前缀>` 离线生成标注图与网格 JSON；`--capture-window <PNG>` 仅在游戏前台时截图；`--traverse-probe <输出目录> <1至10行>` 用独立设备执行有限行数的真实导航，要求关闭 GUI 并从首盘开始。CLI 诊断无 F10 消息循环，切出游戏可停止；日常测试使用 GUI。

`--up-probe` / `--down-probe <输出目录> <1至10次>` 在首列发送有限次纵向脉冲，保存前后截图及 navigation.json；它们不验证每次实际位移，退出码 0 只表示完成记录，不表示已经到顶或到底。不要将上移多次当作自动回到首行：本机实测首行上移会绕到末行。

### 验证范围

0.3.1 的 40 项检查覆盖输入释放、驱动策略、4 种合成布局、末行、回首列、跳格、滚动歧义和黑屏，以及断裂边框、呼吸动画、起步吞键及纵向回绕。0.4.0 增加 8 项 OCR 时序、取消、失败、提交计数及对照顺序检查，共 48 项；另执行实际 ONNX 模型的固定样本回归。全背包、HDR、各分辨率真机与跨电脑运行尚未完成验证。

### 2026-10-21 真实 4K 导航记录

本机 3840×2160 全屏、ViGEmBus 1.21.442.0、D-pad 80ms 按压 / 350ms 释放间隔：动态识别 9 列、4 个可见行。前 5 行验证结果为 `ProbeLimitReached`，确认访问 45 个位置，完成 5 次末列回首列和 4 次下移，共发送 49 次方向输入，用时 45.877 秒（含截图、稳定观测及证据写盘，不含 OCR）。第 4→5 行时焦点保持视觉第 4 行，重叠内容匹配证明列表上滚一行，平均差异为 3.343。

本地证据：仓库 `artifacts/gamepad-live-probe-05/summary.json`、`events.jsonl`、`action-00040-before.jpg` 和 `action-00040-after.jpg`。截图不打入便携包。

本轮实际修正了三类问题：头像截断细边框导致无法起步；呼吸动画及单像素采样导致静止内容被判变化；首次方向输入只完成键鼠→手柄切换。此前失败均有保留日志，未按发送次数补记访问位置。

**边界规则需修订：本机实测纵向也会循环。** 从第 4 行首列发送 4 次上移后到了末行首列，末行可见 5 件（941 = 104×9 + 5）；再单独发送一次下移，回到起始第一个盘及原始整屏内容。证据分别在 `artifacts/gamepad-rewind-01/`（旧诊断命名）与 `artifacts/gamepad-bottom-down-01/`。末行识别和纵向边界已观察，但未逐件遍历整包，也未实测末行横向循环；不得把边界跳转计入已扫描数量。最终已返回首盘，证据在 `artifacts/gamepad-return-first/`。

当前速度约 0.98 个确认位置/秒，仅用于这次短程基线，不能外推所有机器。CPU、峰值内存、长时间截图与日志开销尚未正式测量；后续先保留逐步验证，再测量并优化采样频率与证据保存开销。

## 记录导航规则

请将实际观察写入工具的「记录观察」，按以下顺序逐项验证：

| 场景 | 记录内容 |
| --- | --- |
| 普通位置左右单步 | 是否恰好移动一格；是否自动更新详情 |
| 普通位置上下单步 | 是否保持同一列；对应跨过几个物品 |
| 最右侧继续向右 | 停止、换行还是循环 |
| 最左侧继续向左 | 停止、换行还是循环 |
| 最下可见行向下 | 是否自动滚动；焦点屏幕位置是否变化 |
| 最后一行不足整行 | 是否夹到最后一件、停住或跳转 |
| 相邻同属性驱动盘 | 能否通过选中框确认已移动 |
| 连续输入 10 次 | 实际移动数与输入数是否相符，是否存在连发或漏按 |
| 输入期间切出游戏 | 是否立即终止，返回后是否保持停止 |
| F10、断开、关闭窗口 | 是否释放按键，虚拟设备是否消失 |

先验证单步，再增加次数；更改参数时记录分辨率、游戏帧率、输入模式、按压时长和间隔。左摇杆与 D-pad 的结果分别记录。首次先确定移动语义，不混入排序、筛选与扫描停止规则的变化。

日志位于 `%LOCALAPPDATA%\ZZZ-Scanner.Next\GamepadProbe\probe-*.log`，界面显示完整路径。日志包含 PRESS/RELEASE、实际按压耗时、取消/错误和人工观察。`movement=UNVERIFIED` 表示仅确认已发送输入，没有证据证明游戏移动；不能把它作为“无漏扫”结果。

## 自动检查与本次结果

自检输出文件路径需有可写的父目录。以下使用 `Start-Process -Wait` 等待 WinExe 完成：

```powershell
$probeExe = (Resolve-Path 'Experiments/GamepadProbe/bin/Release/net8.0-windows/ZZZ.GamepadProbe.exe').Path
$reportPath = Join-Path $env:TEMP 'zzz-gamepad-selftest.txt'
Start-Process -FilePath $probeExe -ArgumentList @('--self-test', ('"' + $reportPath + '"')) -WindowStyle Hidden -Wait
Get-Content -LiteralPath $reportPath
```

将 `--self-test` 改为 `--device-check` 可执行真实驱动连接检查。运行设备检查时先断开工具中的虚拟手柄，并避免其他手柄设备同时连接/断开。

`--diagnostics <输出文件>` 导出只读环境检测；`--verify-installer <输出文件>` 校验随包安装器而不运行它。

2026-10-21 验证结果：

- 实验项目和主项目 Release 构建成功，均为 0 警告、0 错误。
- 15 项离线检查通过：原有 9 项输入／释放检查，以及未安装、基准版本、其他版本、未运行、未知版本的分支与篡改安装器拒绝检查。
- 拔掉实体手柄后，设备检查前 XInput 连接槽位为空；程序创建的新虚拟 Xbox 手柄被 XInput 识别为槽位 0。
- 所有按键、扳机与摇杆回中检查通过；释放设备后该槽位恢复断开。
- 驱动检查没有发送 D-pad、确认键或足以导航的摇杆幅度。
- 用户随后确认：通过工具点击上／下按钮并切回游戏，可以移动；前台 F9 等功能键会触发键鼠热切换，不适合作为导航触发方式。这是用户实测反馈，代理未独立观察游戏画面。
- 早期桌面操作工具因原生管道不可用，未完成游戏画面检查；随后通过本项目的截图与手柄诊断入口完成上述真实 4K 前 5 行测试。其余分辨率、左移、末行横向循环和全包完整性仍待系统验证。

本机驱动初始化存在一个值得保留的兼容性细节：`XusbPdo.cpp` 启动 USB 报告包含非零摇杆值，而其缓存初始值为零，重复提交全零报告可能被去重。原型连接后先提交 `LeftThumbX=1`（低于通常的摇杆死区），随即提交全零状态，设备检查确认最终四轴均为零。该初始化也需要在其他驱动版本和游戏配置上验证。

## 后续接入扫描器

0.4.0 已通过编译链接复用现有 OCR、清洗和槽位校验代码，未修改这些共享源码。后续再抽象正式导航后端并对接扫描器导出流程。不得用 PRESS 数量直接更新逻辑 index；应验证选中状态、自动滚动和详情同步。蛇形/按列遍历不能直接沿用遇到非 15 级立即结束的策略。

## 0.4.0 OCR 性能基线与分档提速

### 操作与输出

GUI 默认启用 OCR，验证行数默认为 2。预览网格后，从背包首盘开始，用“基线 80/350/100”运行；三项分别为按压、释放间隔、稳定观测间隔，单位 ms。基线正确后逐档选择提速 1/2/3，仍需从相同起点开始。可取消“接入 OCR”单独测导航。“保存每件详情截图”默认关闭，启用后会增加磁盘用量；失败时自动保留详情图。

每个已确认的位置读取名称、等级、主属性名称/值、四组副属性名称/值，共 12 个区域。品质从当前格子的色条确认，不默认所有盘都是 S。名称、等级及主属性为空或置信度低于 0.65、非空副属性置信度低于 0.65、清洗/槽位校验失败、满级盘缺少四条副属性时立即停止。只有当前位置 OCR 完成并校验通过才继续方向输入；相邻相同文字不合并去重。

目前详情 ROI 复用 `Data/scan_profiles.json` 的 16:9 布局并按实际像素缩放；动态网格识别不代表详情 ROI 支持所有宽高比。非 16:9 会拒绝 OCR，先用网格模式验证布局。稳定门同时比较网格和各详情文字区，要求连续三次观测一致；松开按键后至少等待 180ms 才开始采纳详情。因此释放间隔填 100ms 时另补足 80ms，不把它宣传为实际只等 100ms。GDI 没有渲染帧编号，短程一致性仍不能独立证明所有低帧率场景的详情更新同步。

输出目录新增：

- `ocr.jsonl`：每个位置的原始 12 区文字、置信度、清洗结果、错误/待核对信息、OCR 子阶段耗时。
- `items.json`：已通过校验的现有清洗器输出；这是实验数据，使用前应检查 `ocr.jsonl` 中的名称映射提示。
- `performance.json`：实际截图、网格分析、详情签名、稳定等待、输入按压与释放、OCR 裁剪/预处理/推理/解码/清洗、证据写盘的次数和均值/P50/P95/最大值；同时记录总耗时、OCR 件数/秒、进程 CPU 时间与峰值工作集。父阶段与子阶段有重叠，不能把所有阶段求和。
- `summary.json`：分开报告访问位置数、OCR 成功数、名称映射待核对数；取消或失败不会把未完成 OCR 当作成功结果。

现有词典有旧名称映射，例如原文“荆棘玫瑰”被清洗为“棘刺玫瑰”。0.4.0 保留共享清洗器行为，同时保留原文、写入 `Warnings` / `OCR_REVIEW_REQUIRED` 并在界面显示待核对数量；本次没有自动修改全局词典。基线一致表示同一位置在不同速度下输出一致，不表示这些映射已被人工确认正确。

45 件实测中有 25 件原始名称与清洗名称不同，包含繁简差异和可能合理的纠错，并不等同于 25 件错误；全部保留供核对。

### 本机实测（2026-10-21）

环境为 3840×2160 全屏、9 列、ViGEmBus 1.21.442.0、虚拟 Xbox 360 D-pad、PP-OCRv5 CPU 推理（单 session，4 个 intra-op 线程）。同一批前 18 件逐档测试，每轮结束后只上移一次，确认初始整屏网格恢复，再运行下一档。每档保留相同的完整详情截图，便于公平比较。模型初始化和预热、轮间回退不计入单轮时间；截图、导航、稳定观测、OCR 和证据保存计入。

| 档位 | 按压 / 释放间隔 / 观测间隔 ms | 18 件耗时 | 件/秒 | 与基线逐位置对照 |
| --- | --- | --- | --- | --- |
| 基线 | 80 / 350 / 100 | 21.765 s | 0.827 | 18 件基线 |
| 提速 1 | 80 / 200 / 100 | 18.573 s | 0.969 | 原文与清洗结果全部一致 |
| 提速 2 | 80 / 100 / 50 | 16.648 s | 1.081 | 原文与清洗结果全部一致 |
| 提速 3 | 60 / 100 / 30 | 15.555 s | 1.157 | 原文与清洗结果全部一致 |

提速 3 相对基线吞吐提高 **39.9%**、用时减少 **28.5%**。这是单次逐档短程测量，尚不是长期稳定性结论。日志见仓库 `artifacts/gamepad-ocr-benchmark-01/benchmark.json`，各档目录含原文和性能分解。

随后以提速 3 完成前 **5 行、45 件**，49 次方向输入，**38.719 秒、1.162 件/秒**，包含第 4→5 行自动滚动。前 18 件的原始 OCR 与慢速基线一致；后 27 件通过现有校验但未另跑慢速对照。工具平均占用 **2.18 个 CPU 核心**，进程生命周期峰值工作集 **368.1 MiB**，不含游戏和驱动，不是整机 CPU 百分比。此单轮包含首件冷推理，不含模型构造时间。证据在 `artifacts/gamepad-ocr-fast-five/`；结束后回到了首盘。

### 下一轮优化顺序

四档中每件纯 OCR 推理约 151～155ms，单次全屏 GDI 截图约 58～59ms，网格分析约 19ms；每步至少三次截图。当前先保留提速 3 作为本机短程测试档，不进一步降低 180ms 详情等待下限，也不取消三次稳定观测。

下一轮先测减少截图开销（区域捕获或复用正式扫描器捕获后端），再考虑有界 OCR 队列并行。并行前必须冻结每个位置的截图和序号，限制待识别队列，保持异常立即停止导航；不能用“相邻结果一样”判重复。对每次改动都使用相同位置、相同证据保存设置进行基线对照，再扩大到整包、低帧率和不同分辨率。

开发命令：`--ocr-image <全屏截图> <目录>` 做单帧识别；`--ocr-runtime-check <报告文件>` 验证随包固定样本及真实 ONNX 依赖；`--ocr-benchmark <目录>` 自动执行上述四档各两行，差异或异常立即终止提速；`--ocr-traverse <目录> <1至10行> <按压ms> <释放ms> <观测ms>` 执行单档。真实导航命令要求关闭 GUI、游戏保持前台并从整个背包首盘开始，CLI 用切出游戏停止；日常优先使用带 F10 的 GUI。

相关整改基准：[代码 review 文档](../../docs/CODE_REVIEW_2026-10-12.md)。本原型没有解决 REV-001～REV-009，也没有更改其整改状态。

## 多电脑适配基准（2026-10-21）

先固定一套组合完成跨电脑实验，不为每台电脑开发不同驱动。以下是测试基准，不是已经通过的支持清单。

| 层级 | 固定版本／范围 | 状态 |
| --- | --- | --- |
| 官方驱动安装包 | ViGEmBus Setup 1.22.0 | 作为新机器安装基准；尚未执行干净安装验证 |
| Windows 实际驱动版本 | 1.21.442.0 | 本机设备创建、归零、释放通过 |
| .NET 客户端 | Nefarius.ViGEm.Client 1.21.256 | 使用精确版本约束与 packages.lock.json 固定解析结果 |
| 虚拟设备 | Xbox 360 / XInput | 无实体手柄也可创建 |
| 首轮平台 | Windows 10 x64、Windows 11 x64 | 分别记录系统具体构建号；跨机器结果待补 |
| 首轮游戏客户端 | Windows 本地客户端 | 云游戏、ARM64 不纳入首轮支持承诺 |

**安装包版本和驱动版本分别检查。** [1.22.0 官方发行说明](https://github.com/nefarius/ViGEmBus/releases/tag/v1.22.0)明确指出仅移除更新器，驱动版本保持不变，并记录了就地升级问题。因此不能因为设备管理器显示 1.21.442.0 就判定安装错误；也不能根据驱动版本推断旧更新器已移除。

现有机器的处理规则：

- 已有基准驱动且设备自检通过：复用，不为统一安装包标签强制重装。
- 没有驱动：引导用户安装固定官方安装包，然后自检；如安装程序要求重启，明确记录并处理。
- 其他版本：记录实际版本和设备自检结果，标记未验证；不要直接卸载、降级或覆盖其他手柄软件共用的驱动。
- 0.2.0 已归档官方 `ViGEmBus_1.22.0_x64_x86_arm64.exe`，验证签名为 Nefarius Software Solutions e.U.；SHA-256 为 `89220A7865076B342892F98865F3499FB7C4CFD673159E89D352C360FD014C6A`。随包保留 ViGEmBus、客户端及 .NET 的许可和声明。
- 自动构建使用 `dotnet restore Experiments/GamepadProbe/GamepadProbe.csproj --locked-mode`，依赖锁文件变化必须显式审查。

按环境分组验证，避免只按 CPU/GPU 品牌统计：

| 环境组 | 必测内容 |
| --- | --- |
| 干净 Windows 10/11，无实体手柄 | 首次安装、必要重启、普通用户运行、设备创建和释放 |
| 已有 ViGEmBus | 版本检测、复用、重复启动、退出清理 |
| 有实体手柄或其他手柄软件 | 多设备槽位、目标游戏选用的设备、输入冲突；不要求用户无条件卸载其他软件 |
| 不同游戏性能 | 30/60 FPS 及明显掉帧，单步与连续输入是否漏按或连发 |
| 不同显示配置 | 720p/1080p/1440p/4K，100%/150%/200% 缩放，窗口/全屏；验证焦点、滚动及后续截图坐标 |
| 异常路径 | Alt-Tab、F10、关闭工具、退出游戏、取消倒计时、按压中停止 |

每台机器保存：系统构建号、驱动/安装包/客户端/工具版本、显示配置、游戏帧率、输入模式、按压和间隔参数、日志、人工观察结果。80ms/350ms 是初始参数；固定驱动版本不意味着所有机器固定同一套等待时序。

验收分两层：设备层要求创建、状态与释放正确；游戏层要求指令与实际焦点移动一致，覆盖首尾边界、自动滚动和相同属性盘。建议每台至少完成 300 次有记录的导航以及 3 轮完整背包遍历，并核对遗漏和重复；这些是后续验收目标，当前工具尚不能自动证明完成。驱动安装与设备层可借助干净虚拟机检查，游戏输入和帧率行为需要实体机器验证。
